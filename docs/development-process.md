# 开发流程

本文规定从现行产品/架构规范进入实现后的协作流程。产品范围以 [PRD](./v1-prd.md) 为准，技术约束以 [架构指引](./v1-architecture.md)、[引擎设计](./engine-design.md)、[架构规范](./architecture-guide.md) 及专项规范为准，验证证据以 [验证计划](./v1-validation-plan.md) 为准；本流程不替代这些规范，也不把计划当作已验证事实。

## 1. 开发阶段

按架构指引 §13 的 `M0 → M1 → M2 → M3 → M4 → M5 → M6` 顺序推进。当前从 M0 开始。各阶段的范围和出口完全沿用架构指引 §13；不得因 OpenSpec 变更归档或实现任务关闭而推定阶段出口通过。

| 阶段 | 范围 | 交接要求 |
|---|---|---|
| M0 引擎地基 | 八 crate 骨架、工具/依赖门禁、catalog、无头引擎核心与基础映射/补丁/历史 | 架构 §13 M0 出口逐项有可复查证据；单独登记 V-01 目标、V-06/V-07 基础结果和未完成项 |
| M1 单文档只读 | 原生单窗只读渲染、点击映射、虚拟化、源码视图及相关平台/字体/性能验证 | M0 通过后开始；记录 macOS 实测和未覆盖平台，不扩大 AC 通过声明 |
| M2 可编辑核心 | 编辑、IME、撤销/重做、搜索、保存/自动保存、外改冲突与恢复的最小安全闭环 | M1 通过；开始前完成 V-08 身份/事务方案，出口覆盖 PRD 对应完整操作链 |
| M3 命令与表格 | 编辑命令、表格操作、HTML 原文编辑与格式化 | M2 通过；先冻结 V-07 样例，结构命令具有单步撤销或明确拒绝 |
| M4 插件与主题 | 插件公共契约、内置提供者、预览/导出、主题/设置 | M3 通过；验证插件启停回退、真实导出产物和完整主题行为 |
| M5 应用壳 | 标签、多窗、工作区、文件树、平台集成和逐 tab 生命周期 | M4 通过；按 V-01/V-08/V-09 逐平台验证 |
| M6 收尾 | 全量验收、性能/资源、打包与发布门禁 | 所有阶段出口及 V-01～V-09 发布阻塞产物完成，三平台门禁均有证据 |

后续阶段可以准备样本和调查风险，但不可绕过前置阶段的安全出口接入依赖功能。阶段完成需回填架构阶段状态和验证计划证据，明确通过项、失败项、未执行项、平台与环境。

## 2. OpenSpec 变更流程

OpenSpec 使用仓库根目录 `openspec/` 下的 `spec-driven` schema，所有新工件使用简体中文。`openspec/changes/` 管理**拟议变更**及其实现任务；`openspec/specs/` 保存主规格。[代码与架构执行规范](../openspec/CODE_STANDARDS.md)和[工程治理主规格](../openspec/specs/engineering-governance/spec.md)是后续实现必须遵循的工程基线，约束模块划分、抽象/模式和交付；现行产品、引擎与专项契约仍由对应 `docs/` 负责。工程主规格不是未确认提案，也不代替已有契约或验证证据。

1. **建立变更。**新增/改变用户可见行为、PRD/AC、跨模块契约、依赖/架构边界、阶段范围或验收方式时，先创建 OpenSpec change。说明背景、目标、非目标、影响阶段/文档、风险与可验收结果；对应需求按 capability 编写增量 spec，架构方案和任务拆解分别写入 design/tasks。
2. **核对基线。**提案必须引用现行规范的具体章节及决定记录。OpenSpec 与 `docs/` 有冲突时，暂停受影响实现，把冲突列为待裁决；OpenSpec 草案本身不能修改已确认契约。只需澄清的实现细节可以在变更设计中说明，不得借机扩大产品范围。
3. **评审后实施。**任务拆成可独立审查的步骤，先做纯逻辑机制，再做 UI；依赖准入、坐标、保真、错误/拒绝、文案和安全边界依对应规范验收。design 按执行规范 §3～4 写清模块/状态所有者、依赖方向、抽象及设计模式解决的问题、最简单方案、代价与验证；简单实现可明确沿用具体类型/函数。模块拆分按职责和生命周期，行数只作复核信号。若实施中需求或契约发生变化，先更新提案/spec/design/tasks 并重新评审，再继续依赖该变化的代码。
4. **验证并回填。**按 Rust 规范及变更任务执行适用检查，记录命令、结果和环境。将已确认/实现的规范正文回写到对应 `docs/`；将实验结果回填 `docs/v1-validation-plan.md`。不能用生成代码、测试通过或 OpenSpec archive 替代平台实验或阶段出口。
5. **归档。**只有实现及适用验证完成、delta 同步至主规格并校验、文档回填一致后才 archive OpenSpec change。归档记录是变更历史，不是现行规范的第二份权威副本。工程规则变更同步 CODE_STANDARDS、工程治理主规格和相关现行文档；主规格不把未实施门禁写成已启用。

不改变产品行为/规范的局部实现修复，可使用短任务直接实施，但仍需关联阶段、需求/缺陷和验证结果；若发现规范缺口或行为分歧，应先转为 OpenSpec change。

## 3. 单项实现的执行顺序

1. 阅读 AGENTS.md 的文档地图、OpenSpec 代码与架构执行规范及工程治理主规格；依据工作范围再读 PRD、架构、引擎、架构/Rust 及相关 UI/插件/主题规范。直接实施的局部修复同样适用这些工程约束。
2. 定位所属 M 阶段、PRD AC、架构模块和验证计划 V 项；未能定位时先澄清规范归属，不自行创造验收口径。
3. 写清输入、输出、状态所有者、拒绝/失败/取消语义、兼容边界和应覆盖的样例。新增依赖先过依赖准入；新引擎机制先用纯逻辑测试表达不变量，再接 UI。
4. 实现最小闭环，维护者边界和源码真源约束优先；同步更新 OpenSpec 工件及权威规范/验证记录。
5. 运行适用的检查并记录证据。M0 workspace 建成后，采用 AGENTS.md 列出的 fmt、clippy、test 命令；在 Cargo workspace 尚未建立前，不声称这些命令已通过。
6. 复核工程治理场景、架构规范检查组、Rust 规则矩阵、PRD AC 和阶段出口；新增/修改自动守卫须以正例和最小违规反例证明有效，重要架构/API/安全/并发/重构按 AGENTS 路由独立审查。记录人工检查与自动化盲区，确认无越界行为、未记录的平台缺口或未回填文档后，才完成该变更。

提交使用 Conventional Commits 和 AGENTS.md 的 scope 规则。CodeGraph 用于代码存在后的符号/调用关系探索；重构或新增代码后运行 `codegraph sync`，并在提交前确认 `codegraph status` 无陈旧索引。CodeGraph 索引数据库为本机生成物，不提交。
