### RS-01 · 额外 lint 的统一基线

- **问题：**除默认诊断、`-D warnings` 和落实铁律的专项检查外，是否统一启用 Clippy `pedantic` 整组？
- **背景与依据：**旧 §2/附录 B 全开 all/pedantic，却全局放行截断/符号丢失，并把 UI missing_docs 豁免混入继承样例；现仓库无配置，AGENTS.md 只明确标准命令和引擎 unwrap 红线。
- **影响：**M0 workspace lint、成员/测试差异、warning 负担与 CI 稳定性；不改变本稿 API 文档、受检转换等语义要求。
- **可选方案：**A（**建议**）默认 lint + 逐项启用铁律/高价值 lint，记录适用层和正反样例，pedantic 按项引入，配置较小但需维护覆盖表。B 全组 pedantic，噪音逐项最小豁免，覆盖较广但升级/平台差异需更多维护；不能复制全局坐标 cast 白名单。两方案都保持 `-D warnings`，`missing_docs` 等独立 lint 的具体级别随范围验证登记。
- **是否阻塞：****可暂按已有约束推进**；阻塞额外 lint 配置冻结，不阻塞按铁律编写逻辑及测试。
- **暂行处理：**不写未裁决 lint 表；按本稿人工/类型/测试要求复核，M0 在已定三命令之外保留待选配置位置。

### RS-02 · 跨模块坐标 API 的强制分型范围

- **问题：**跨模块/跨 crate 的源码、绘制、UTF-16 偏移是否统一要求 newtype？
- **背景与依据：**旧 §5 要 B+ 时 `SrcOff`/`DrawnOff`/`Utf16Off` 化；当前架构允许分型或明确命名，引擎 §7 没冻结具体 Rust 类型，AGENTS.md 同时要求补丁表示为 `Vec<(Range<usize>, String)>`。没有已有 TA/ED/AG 决定可直接替代。
- **影响：**M0 公共映射/选区 API、类型 home、范围与版本封装、转换开销及后续签名兼容；需关联 V-07，不得新增反向依赖。
- **可选方案：**A（**建议**）跨边界 newtype/受检范围，模块内部单坐标可用明确命名 usize；在补丁表示边界受检转换，不更改铁律规定的补丁形状。可在编译期挡混用，适配代码较多。B 允许带单位/版本文档和命名的 usize/Range，通过私有构造/映射 API 与测试控制；初期简单，调用者仍可能混传。
- **是否阻塞：****阻塞后续实现**中的公共坐标签名最终冻结；不阻塞无头映射金样、受检算法及私有原型。
- **暂行处理：**只描述语义/命名/校验，不定型名、底层宽度或 crate 归属，不借 newtype 重定义 buffer/markdown 分层；API 冻结前等待裁决，V-07 验证两类表示的正确性边界。

### RS-03 · 内部缺陷与测试夹具的 panic 类操作例外

- **问题：**对已证明不由外部输入触发的内部不变量、UI 初始化和测试夹具，是否允许 `expect` / `panic!` / `unreachable!` 及发布期 `assert!`？
- **背景与依据：**旧 §1/§7 宽泛允许引擎不变量 expect 和 UI pragmatism，附录又把 expect_used warn 配合 -D warnings；AGENTS.md 明确引擎禁 unwrap、用户输入不 panic，并优先 debug_assert，却未统一上述例外政策。当前架构 R-16-01 同样只确定受检外部错误边界。
- **影响：**错误出口、测试辅助函数、expect/panic lint 范围及缺陷诊断；任何选择都不得允许引擎 unwrap 或输入路径崩溃。
- **可选方案：**A（**建议**）引擎生产代码不用这些退出操作，以显式错误/拒绝 + 内部 debug_assert 为基线；测试预期断言允许，测试夹具/UI 启动例外逐处证明和最小 lint 记录。边界清楚，但可能增加错误分支。B 内部不变量路径允许逐处例外，记录外部不可达证明、失败影响及测试；诊断直接，但评审/升级时需持续证明。二者均不允许用 should_panic 接受坏输入崩溃。
- **是否阻塞：****可暂按已有约束推进**；仅阻塞依赖 panic 例外的实现及对应 lint 放行。
- **暂行处理：**使用 Result/拒绝和内部 debug_assert，不默认采用 A/B，不沿用旧 expect 白名单；引擎测试同样不写 unwrap。

### RS-04 · unsafe lint 基线及平台例外机制

- **问题：**本仓库 unsafe 采用统一 forbid，还是 deny + 最小平台模块例外？
- **背景与依据：**旧 §11/附录 B 要 workspace forbid，又允许未来 crate 降 deny，没有说明继承后的有效配置；AGENTS.md 与当前 PRD/架构未确定统一 unsafe 政策。平台 API 的真实需要另由 V-01 验证，不能仅因原生应用就预放行。
- **影响：**workspace/成员 lint、FFI 包装、平台构建、安全评审与未来配置变更路径；不扩张平台/外部插件范围。
- **可选方案：**A（**建议**）自有代码默认 forbid，真实平台需要时另提规则例外方案，明确受影响 crate 的有效配置及保留其他 lint 的方式；日常边界最强，例外需改配置。B 基线 deny，裁决后的平台适配模块可最小 allow，附 SAFETY/安全 API/独立评审及验证；实施灵活，但须防止例外扩散。
- **是否阻塞：****可暂按已有约束推进**；阻塞 unsafe lint 最终配置及任何自有 unsafe/unsafe impl 的引入，安全 Rust 引擎工作可继续。
- **暂行处理：**不建立 forbid/deny 配置，不引入依赖该例外的分支。S-10-01 先准备可审查证据，不以第三方依赖含 unsafe 自动放行。

### RS-05 · 非单一 crate 变更的提交 scope

- **问题：**纯文档、workspace 配置及必须一起提交的跨 crate 变更使用什么 scope？
- **背景与依据：**AGENTS.md 及旧 §16.2 要 scope 用 crate 名，未说明没有所属 crate 的变更；当前本轮就是 docs 变更，不能虚构一个 crate 名或静默违背规则。
- **影响：**提交历史、后续 commit 检查与跨 crate 原子变更的可审查性；不改变 Conventional Commits 主格式。
- **可选方案：**A（**建议**）单 crate 保持完整名；无单一归属时允许有限的 `docs`/`workspace`/`app` 等真实范围，跨 crate 用主责 crate 并在正文列其余范围，约定清楚但需维护范围表。B 单 crate 保持原要求，其余允许省略 scope，规则较少但检索归属较弱。若 `app` 是实际包 scope，以 M0 package 名为准，不假定与目录永远同名。
- **是否阻塞：****可暂按已有约束推进**；仅阻塞无单一 crate 归属的正式提交格式，本轮文档交付不需要创建提交。
- **暂行处理：**不代选例外、不创建提交；裁决后同步 AGENTS.md/本节及未来提交检查，不新建未经决定的自动审批工具。

### ED-01 · 组合未结束时显式保存或导出的快照时机

- **问题：**中文 IME 仍有未确认 marked text 时，用户显式手动保存、另存为或导出，应等待平台组合结束后取快照，还是立即发布包含当时预编辑候选的快照？
- **背景与依据：**PRD EDIT-05/06 要求候选/确认/取消正确、IME 确认独立成组且快照不改变历史；SAFE-04 只明确自动保存延后，EXPORT-01 要求导出包含当前块最新内容。架构 §7.3 将恢复组合表示交 V-07/V-08，却未定义显式发布未确认候选的行为。旧引擎 §2.8/2.9 的“快照/保存前 flush”不能回答，且隐式确认/封口违反 TA-01。此问题不同于组合已结束后的普通草稿保存，也不重开 TA-01。
- **影响：**M2 手动保存/另存为、M4 导出请求调度；输入快照是否允许 Preedit 发布、保存内容身份、取消组合后的 dirty、AC-03/05/14 及 V-07/V-08 样例。不会改变补丁或历史的基本模型。
- **可选方案：**A（**建议**）显式请求进入可取消的等待状态，平台自然确认或取消后对结束后的当前文本取快照；不伪造确认、不发布临时候选，但请求可能延后。B 立即冻结并发布含 marked text 的当前快照，反馈其预编辑身份，随后取消组合会令内存与已保存/导出内容不同；速度直接，但未确认候选会进入外部文件，需明确提示与保存身份处理。C 组合期间明确返回“输入尚未完成”，待用户结束后重试；不会写出预编辑内容，实现简单，但不自动延续原请求。
- **是否阻塞：****阻塞后续实现**中的组合期显式保存/另存为策略与 M4 组合期导出完整验收；不阻塞 M0/M1、普通已确认输入、自动保存延后或恢复快照保护。
- **暂行处理：**输入快照显式携带组合状态，发布请求保留 request_id/输入状态门控接口；不默认 A/B/C、不执行该待决分支。自动保存按已定延后，恢复仍保护当前输入及临时资源；不靠计时器强制确认来绕开问题。
- **裁决后建议回写：**PRD SAFE-04/EXPORT-01（并交叉引用 EDIT-05/06）、架构 §7.1/7.3/8.3、本文 §8.3/10.1，以及 V-07/V-08 的操作序列。当前未修改这些上游文件。
